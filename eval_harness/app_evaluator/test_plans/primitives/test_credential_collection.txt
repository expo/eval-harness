<test_plan>

<purpose>
Primitive: Identity → Sign-in → Credential collection (APP-AGNOSTIC).
Verify that the app's sign-in / authentication surface renders a usable credential-collection UI: at least one credential input is present, each input accepts typed input (with appropriate masking for password-type fields), and a submit / unlock affordance is exposed and reachable. This test does NOT assess credential correctness or sign-in outcomes — do not attempt to actually submit credentials for evaluation here, only verify the surface is well-formed.

This test plan is APP-AGNOSTIC: it must apply to any app's credential-collection surface, whether that is a fixed-password gate, an email + password login, a multi-step signup, or another variant. Use the supplied app PRD to determine the specific shape of this app's sign-in surface and map the abstract verifications below onto its concrete elements.
</purpose>

<seeding_and_precondition>
Before performing the formal verifications, read the supplied App PRD to determine the shape of this app's sign-in surface:

- WHAT IS COLLECTED: a single password? email + password? username + password? role selection? something else? The set of "credential inputs" for this primitive is whatever the PRD specifies the sign-in flow accepts at the first credential entry screen — not subsequent profile-completion or onboarding fields.
- WHERE: which screen / route is the credential-collection surface on a fresh app launch? If the app launches directly into it (e.g., a password gate that gates all content), no navigation is needed. If the app launches to a landing or marketing screen, navigate to the sign-in / login affordance.
- MASKED FIELDS: which of the credential inputs are password-type (secureTextEntry) and should mask typed characters? Email / username fields should generally NOT be masked.

If the PRD indicates the app has no sign-in flow at all (e.g., "session-based, no accounts" or "single-user, no auth gate"), this primitive does NOT apply to this app. In that case, do not record any assertions and immediately complete_step with the note "N/A: PRD indicates app has no credential-collection surface." This will be recorded as not-applicable.

No data needs to be seeded for this test.
</seeding_and_precondition>

<steps>
<step>

<name>
test_credential_inputs_render_and_accept_input
</name>

Navigate to the credential-collection surface if you are not already there.

Locate the credential input field(s) the app uses for sign-in.

Verify:
- At least one credential input field is present and visible on the sign-in surface
- For each credential input that is password-type (according to the PRD and the element type in the accessibility tree, e.g. `securetextfield`), the field is MASKED — when a character is entered into a password-type field, the field displays a placeholder dot / asterisk / bullet, NOT the literal character
- (non-fatal) Each visible credential input has a label, placeholder, or accessible description that identifies its purpose (e.g. "Password", "Email", "Username")

Tap into ONE of the credential input fields (any one; the password field if there is one — otherwise any input). Type the arbitrary string `abc` (three characters; this is not a real credential, just an input-acceptance probe). Do NOT submit the form — leave the field with `abc` entered and stay on the sign-in surface.

Verify:
- The field accepts the input (the field visually reflects that three characters have been entered, whether masked or in plain text)
- For password-type fields tested in this step, the literal characters `abc` are NOT visible in plain text within the field; for non-password fields, plain `abc` is acceptable and expected

<points>5</points>
</step>

<step>

<name>
test_submit_action_is_reachable
</name>

On the same credential-collection surface, observe the submit / sign-in affordance. Do not interact with it — only confirm its presence and reachability.

Before assessing reachability, dismiss the on-screen keyboard if it is still visible from the typing in the previous step. The keyboard occupies a substantial portion of the screen on iOS and can visually obscure submit affordances at the bottom of the credential-collection surface. Use a coordinate tap on a non-interactive area (the screen header, a title area, or empty space above the keyboard) to dismiss the keyboard before judging whether the submit affordance is reachable.

Verify:
- A submit / sign-in / unlock action is exposed to the user, in any of the following forms:
  - A visible button labeled something like "Unlock", "Submit", "Login", "Sign In", "Continue", or similar (the exact label depends on the app's PRD-specified terminology)
  - A submit-on-Enter / submit-on-Return-key affordance on the credential field
  - A tappable arrow / icon button positioned with the credential input(s)
- The submit affordance is reachable (not visually obscured by the keyboard, by another overlay, or off-screen)

<points>2</points>
</step>
</steps>

<full_points>7</full_points>
