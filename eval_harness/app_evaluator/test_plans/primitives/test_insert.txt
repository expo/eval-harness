<test_plan>

<purpose>
Primitive: Data → Record CRUD → Insert (APP-AGNOSTIC).
Verify that the app supports creating a new record of its primary entity type. After the create action completes, the new record appears in the relevant list / feed / catalog with the expected derived representation (title, preview, timestamp, or whatever the PRD specifies for a row in this app).

This test plan is APP-AGNOSTIC. Use the supplied App PRD to determine: what the app's primary entity is (note, post, flight, venue, wedding request, etc.), how the user creates one, and how a newly-created entity is represented in the list/feed afterward.
</purpose>

<seeding_and_precondition>
Read the supplied App PRD to determine:

- ENTITY: what is the primary record this app lets users create? Notes (note), Family Social (post), Pilot Logbook (flight entry), Wedding Venue (a venue listing for managers, or a wedding-request booking for couples — pick whichever is simpler given role assumptions), etc.
- CREATE AFFORDANCE: how is "create new" exposed? Common patterns: a "+" button, a "New X" button, a floating action button, a Compose tab.
- REQUIRED FIELDS: what fields must be filled to successfully create a record? Use throwaway but PRD-compliant values for each (e.g. unique strings, valid emails, decimal hours, valid dates per PRD constraints).
- LIST REPRESENTATION: after creation, what does the new record look like in the list / feed / catalog? Title text? A preview? A testID-bearing row?

Setup for the formal test:
- Navigate to the create affordance per PRD. This may include signing in if the app gates content behind auth (check the PRD for credentials).
- DO NOT actually create the record in setup — leave that to step 1 of the formal test.

If the PRD indicates the app has no persistent records the user creates (session-based only, no accounts, read-only browsing), record this primitive as not-applicable and immediately call complete_step with the note "N/A: PRD indicates app has no user-creatable persistent records."
</seeding_and_precondition>

<steps>
<step>

<name>
test_create_affordance_opens_creation_surface
</name>

From the screen where the create affordance lives, tap it (the "+", "New X" button, FAB, or whatever the PRD specifies).

Verify:
- The creation surface is now visible (a new screen, a modal form, an inline editor — whichever the PRD specifies)
- An input or set of inputs corresponding to the PRD's required fields is visible and ready to accept input
- (non-fatal) The creation surface is reachable from the same screen the agent started on (the create affordance worked, didn't dead-end into an unrelated screen)

<points>3</points>
</step>

<step>

<name>
test_new_record_appears_in_list_after_creation
</name>

Fill the required fields with PRD-compliant throwaway values and complete the creation flow (save, post, submit, etc., per the PRD's terminology). Then navigate to the list / feed / catalog that should display the new record (if you're not already on it after creation).

Verify:
- A row / item / card representing the just-created record is now visible in the list / feed / catalog
- The new record's primary identifying field (title, name, first line of body, etc.) matches the value the agent entered during creation (uses PRD-specified derivation rules where applicable, e.g. "title = first non-empty line of body")
- (non-fatal) The new record displays the metadata the PRD specifies for a row (timestamp, author, status indicator, preview text) — agent reports which ones are visible

<points>3</points>
</step>
